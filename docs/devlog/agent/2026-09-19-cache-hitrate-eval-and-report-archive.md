## 背景

外部评审质疑「缓存命中率」相关数字后，发现两个既有脚本都撑不起这个指标：

1. `eval_semantic_cache.py`（E6）：只有 **1 条原 query × 3 条同义改写**，命中率只能取
   0/33/67/100，样本量不足以报百分比。
2. `eval_cache.py`：3 轮用的是**完全相同的 query 字符串**，测的是「原文重复」不是
   「同义改写」；且它的「embedding 调用下降 66.7%」有三处不成立（见下）。

所以按用户要求新建专项测试：① 相同语义不同 query 的命中率；② 有无缓存的
embedding 调用率。

## 改动

### 1. 新增 `src/ragas_test/eval_cache_hitrate.py`（E6-B）

- 语料：**12 组**技术类 query × **3 条同义改写** = 36 条改写查询；
  负样本分两类——硬负样本 8 条（**同域不同问**）、跨域负样本 6 条。
- 三个维度：
  - **隔离会话**：每个 thread 只存 1 条缓存，测纯语义匹配上限。
  - **混合会话（规模梯度 1/3/6/12 条）**：生产真实形态，额外判定「命中的是不是那一条」
    （命中但条目错误 = 缓存污染，比不命中更危险）。
  - **KNN 候选召回诊断**：直接拉 top_k=12 长榜，统计正确条目排名，定位命中率上限。
- **embedding 计数改为按「实际嵌入的文本条数」**：只给 `embed_documents` 打补丁。
  旧 `EmbeddingCallCounter` 同时打 `embed_query` + `embed_documents`，而
  `OpenAIEmbeddings.embed_query` 内部转调 `embed_documents([text])`——**一次被计成两次**
  （120/40 的真实值是 60/20）。脚本启动自带计数口径自检，不通过直接终止。
- **检索嵌入宽度实测**：真实调用 `rewrite_query`，实测每条 query 检索阶段嵌入
  **4** 条文本（原问题 + 1 主查询 + 2 子查询，6/6 样本 min=max=4），
  作为「无缓存基线」的依据，而不是拍脑袋。
- 延迟同时报 **p50/p95/max**：外部 API 偶发长尾（本次最坏 120 s 停滞），均值会被拉偏。

## 结果（两次独立运行，命中率完全一致）

| 场景（缓存条目数 / KNN top_k） | 命中率 | 条目错误率 | p50 |
|---|---|---|---|
| 隔离会话（1 / 3） | 97.2%（35/36） | 0% | 327 ms |
| 混合 1 / 3 | 100%（3/3） | 0% | 309 ms |
| 混合 3 / 3 | 100%（9/9） | 0% | 416 ms |
| 混合 6 / 3 | 77.8%（14/18） | 0% | 341 ms |
| 混合 12 / 3（**生产默认**） | **61.1%**（22/36） | **0%** | 367 ms |
| 混合 12 / **12** | **88.9%**（32/36） | 0% | 427 ms |

- 误命中率：硬负样本 **0/8**、跨域 **0/6**。
- KNN 排名分布：第 1 位 36.1% / 2~3 位 25.0% / 4~5 位 5.6% / 6 位以后 22.2% /
  不在 12 条长榜内 11.1% → recall@3 **61.1%**、recall@12 **88.9%**。
  **命中率 ≈ recall@top_k**，即瓶颈在 KNN 候选数，不在 reranker 阈值 0.5。
- embedding 调用率（24 条 query 流）：无缓存 **96** 条文本（4.0/query）vs 有缓存 **84** 条
  （3.5/query），**实测降 12.5%**；按命中率换算降幅 26.4%（h=61.1%）~ 75%（h=100%）。

## 「embedding 调用下降 66.7%」作废的三条理由

1. **基线选错**：3 轮全部开着缓存，比的是「冷启动有缓存」vs「热态有缓存」，不是有无缓存。
2. **计数重复**：真实嵌入文本数 60/20，不是 120/40（比例不变，绝对值翻倍）。
3. **场景不符**：完全相同的 query 字符串 = 原文重复，撑不起「语义缓存」的说法。

新口径下还有一个**必须带上的前提**：`query_cache` 自己要先嵌入 1 条
（`cache_service.py:202`），缓存省的是「4 条检索嵌入」。敏感性分析显示改写宽度 = 3 时
降幅 **0%**、= 2 时**反而 +25%**——收益完全依赖「检索嵌入条数 > 3」。
