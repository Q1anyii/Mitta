## 背景

H-11（`a42e5e3`）把 `persona_router_node` + `classify_node` 两次串行 LLM 合并为单个
`router_node` 后，两个遗留问题一直没闭环：

1. `eval_routing.py` 仍 `import classify_node`——该节点已**被主图摘除、仅保留未删**。
   其 94.12% 测的是废弃节点，不能作为现役路由能力的证据。
2. 首 token 只测「一条检索类 query 重复 5 次」，合并后首 token 前的链路已分三档，
   单场景测量无法体现合并收益，且重复会命中检索语义缓存（测到热路径而非冷路径）。

## 改动

### 1. `eval_routing.py` → 统一路由评测（37 条，双维度）

- 白盒调用现役 `router_node`，**一次调用同时统计 `persona` 与 `need_retrieval`**
  （更贴合架构，且比 E1+E15 分开跑省一半 LLM 调用）。
- 用例集合并：原 E1 意图路由 18 条（补齐第 10 条「工具调用死循环是怎么防护的？」，
  旧版 `build_cases` 截断未纳入）+ E15 人格 16 条 + 短路专项 3 条 = **37 条**，
  脚本内置去重自检。
- **标注约定**：`need` / `persona` 为 `None` 表示该维度不参与统计。用于排除语义多解
  （如「帮我算 12+34」）与短路路径（`persona` 取 `DEFAULT_PERSONA`、不经模型）的用例，
  避免主观标注人为制造假失败。
- 新增 `--temperature`（默认 0）与 `--repeat`（默认 3，取众数）消除采样波动；
  报告中落盘 `config` 记录两者。
- 断言：① 用例集无重复 query；② 短路用例耗时 >50ms 告警（疑似未走短路）。

### 2. `eval_sse.py` → 分场景首 token

- 三档场景：`shortcut`（0 次路由 LLM）/ `no_retrieval`（1 次）/ `retrieval`（1 次 + 检索链路）。
- 每场景多条不同 query（避免重复命中语义缓存）、预热请求不计入统计、
  `cold`/`warm` 分离统计、默认端口 8000 → 18000（对齐 `.env MITTA_API_PORT`）。
- 污染模式表新增 `router_node` / `persona`（`classify_node` 保留以检测旧版本输出）。

### 3. `persona_router_eval.py` 标记 deprecated

16 条人格用例已并入统一评测，报告冻结为 `persona_router_eval_report.LEGACY.json`。

## 发现的问题（未修）

1. **`temperature=0` 仍不可复现**：两次同参数重跑 91.43% / 94.29%。已改为只报区间。
   若需硬结论需 `--repeat 5~7` 或多 prompt 版本对照。
2. **`ROUTER_PROMPT` 检索判定语义边界模糊**（设计问题）：稳定失败 2 条——
   「查一下今天南昌的天气」「分析一下这段报错堆栈」被判 `need_retrieval=True`，
   但按设计应走**工具**而非**知识库检索**。根因是 prompt 未区分
   「需要外部信息（→工具）」与「需要知识库检索（→RAG）」两条路径。
3. **旧 94.12% 的成因已定位**：`CLASSIFIER_PROMPT`（`constant/prompt_constants.py:26`）
   仍是「在线学习平台」业务路由文案，与 Mitta 技术文档知识库主题脱节。现役
   `ROUTER_PROMPT` 已重写为通用判定，原失败项「Rerank」在新节点上两次均判对。
4. **首 token 无本地基线**：本地后端 `:8080` `/health` 返 500
   （`chat_service.check_db_health` 失败）。改测线上，但线上含公网往返、
   且镜像不含未推送提交，**不代表当前 HEAD**。
5. **路由能力无 CI 门禁**：`tests` 73 条全是纯函数回归，不含 LLM 用例
   （`agent-regression.yml` 刻意排除），路由只有离线评测一个入口。
