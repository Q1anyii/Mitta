# Mitta MCP 冷启动"容忍 vs 根治"深度分析 开发日志

> 涉及模块：MCP 客户端（`src/mcp_client/client.py`）、聊天服务（`src/service/chat_service.py`）、启动入口（`src/main.py`）
> 关联提交：`5a2b2fd`（超时 15/20s→120s）、`8abfb39`（外层等待 30s→130s）、`d8abc33`（devlog）、`bbebdff`（移除 playwright）
> 性质：架构分析（本轮未改代码，结论供后续决策）

---

## 一、问题来源

外部评审引用 commit 记录"本地 MCP 冷启动连接超时全跳线修复日志（15/20s->120s）"，提出质疑：

> MCP 工具通过 stdio 启动子进程，冷启动延迟是个老大难问题，作者把超时从 15-20 秒拉到 120 秒——这本质是"容忍问题"而非"解决问题"。用户发一条消息等两分钟才收到回复，体验可想而知。

**核心指控**：120s 超时 = 用户发消息要等 2 分钟。要判断这个指控是否成立，必须回答两个问题：
1. **120s 超时发生在哪条链路上？**（启动时 vs 用户请求时）
2. **用户发消息真的会阻塞等待 MCP 连接吗？**

---

## 二、排查过程（读代码确认事实）

### 第 1 步：定位所有 MCP 连接调用点

| 调用点 | 时机 | 超时 | 是否阻塞用户 |
|--------|------|------|-------------|
| `main.py` lifespan：`init_mcp_holders(load_mcp_server_configs())` | 后端启动时 | `.result(timeout=130)` | **否**——后端启动阶段，用户无感知 |
| `chat_service._rebuild_user_graph_async`：`init_mcp_holders(user_servers, timeout=120)` | 用户首次请求时 | `.result(timeout=130)` | **否**——后台线程，不阻塞 SSE |
| `make_sync_tool` 工具调用 | 实际调用工具时 | `TOOL_CALL_TIMEOUT=30` | 仅工具执行，非连接 |

### 第 2 步：确认用户请求路径是否被 MCP 连接阻塞

`chat_service._get_user_graph(user_id)` 的关键逻辑：

```
用户有自定义 MCP 配置？
├─ 无 → 直接返回全局图（启动时已连接好）
├─ 有，缓存命中且 hash 未变 → 返回缓存图（工具已在）
└─ 有，缓存未命中
    ├─ 有旧缓存 → 后台重建 + 返回旧图（本次请求不等待）
    ├─ 失败冷却期内 → 返回全局图（不重复触发）
    └─ 无缓存 → 触发后台重建 + 返回全局图（本次请求不等待）
```

**关键结论**：用户发消息时 `_get_user_graph` **从不等待** MCP 连接完成——缓存未命中时后台异步构建，请求先拿全局图继续走 SSE。评审说"用户发消息等两分钟"**在当前架构下不成立**。

### 第 3 步：确认 120s 超时真实发生在哪里

- **后端启动**：lifespan 里并发连接全局 11 台默认服务器，120s 是"最坏情况"上限（uvx/npx 首次下载依赖）。这是**启动慢**，不是"用户等"。
- **用户图后台构建**：首次配置自定义 MCP 后第一轮请求触发后台构建，120s 是构建上限。构建期间用户已拿到全局图回复。

### 第 4 步：识别仍然存在的真实体验问题（容忍残留）

| # | 问题 | 影响 |
|---|------|------|
| 1 | **构建完成不注入当轮**：后台构建成功后写缓存，但**当前这轮请求已经用全局图回复完**，用户专属工具要等**下一次**请求才生效 | 首次配 MCP 后第一轮对话没有新工具 |
| 2 | **坏服务器占满超时窗口**：某台 server 启动即失败/无响应时，后台构建任务被拖满 120s 才收尾，期间构建结果不可用 | 有坏配置时新工具生效延迟 = 超时值 |
| 3 | **依赖下载是主成本**：uvx/npx 首次运行下载依赖（chromadb 22.5MiB、markitdown 71 包、basic-memory 169 包），缓存后才是秒级 | 服务器冷启动/新包首装时慢 |

---

## 三、结论：指控 vs 事实

| 评审指控 | 事实 |
|---------|------|
| "用户发一条消息等两分钟才收到回复" | ❌ **不成立**。请求路径从不等待 MCP 连接（后台异步 + 全局图兜底） |
| "120s 是容忍问题" | ⚠️ **部分成立**。120s 是启动/后台构建的超时上限，不是用户等待；但坏服务器拖满窗口 + 工具下一轮才生效，确实是"容忍" |

---

## 四、根治方案（候选，未实施）

| 方案 | 做法 | 收益 | 成本 |
|------|------|------|------|
| **A. 构建完成主动注入当轮** | `_rebuild_user_graph_async` 完成后，若当前请求的 graph 引用还是全局图，替换为新建的用户图（需请求持有可变引用或重建当前消息链） | 首次配置立即生效 | 中——涉及运行时替换图实例，LangGraph 已编译图替换有风险 |
| **B. 坏服务器快速失败** | 连接失败即刻返回（不等到 120s），或对已知坏配置跳过（失败标记 + 冷却，已有 60s 冷却），把"最坏 120s"压到"秒级失败" | 后台构建不拖尾 | 低——`_connect_one` 已有 try/except，加快速失败分支 |
| **C. 镜像内全量预热** | Dockerfile 构建期对全部默认服务器 `uvx/npx --help` 预热缓存（当前已预热 6 包） | 容器冷启动秒连 | 低——CI 构建时间 +镜像体积 |
| **D. 服务器常驻** | 独立进程常驻所有 MCP server，应用通过 socket/HTTP 复用（非 stdio 拉起） | 彻底消除冷启动 | 高——架构改动大，运维复杂度上升 |

**建议**：短期先做 B（坏服务器快速失败）+ C（预热补全），把最坏场景从"拖满 120s"降为"秒级失败"；A 作为体验优化（首次配置当轮生效）单独立项；D 留作远期（与 MCP 服务器数量规模化需求挂钩）。

---

## 五、经验沉淀

1. **超时值不等于用户等待时间**：排查"等多久"问题，先画调用链，区分启动时/请求时/后台线程——120s 在启动和后台，用户请求路径根本不碰它
2. **异步构建 + 旧图兜底是防阻塞的好模式**：`_get_user_graph` 缓存未命中先返回全局图、后台构建、失败冷却，三层保障让 MCP 连接与对话响应彻底解耦
3. **"容忍"残留要具体化**：不是"超时大"就一定差，而是"坏服务器拖满窗口"和"工具下一轮才生效"这两个具体点才是优化目标——根治也要对症下药
4. **先预热后超时**：uvx/npx 冷启动主成本是依赖下载，镜像构建期预热缓存 + 合理超时双管齐下，比单一加超时健康
