# Agent 推理与规划

> 基于 AgentProject 项目总结，涵盖思维链（CoT）、意图分类、任务路由、工具选择规划、
> 结构化输出等推理与规划能力，以及 Mitta 统一路由与工具装配的实际实现。

## 一、Agent 推理基础

### 1.1 思维链（Chain-of-Thought, CoT）

让模型在给出答案前先输出推理过程，能显著提升复杂推理的正确率：

```
Q: 缓存命中率 61.1%，embedding 调用从 96 条降到 84 条，降幅多少？
A: 降幅 = (96 - 84) / 96 = 12 / 96 = 12.5%
```

**实践要点**：
- 推理过程放在内部（或显式输出），最终答案用结构化格式返回
- 需要模型"展示步骤"的场景（教学、排障）适合显式 CoT
- 简单问题不加 CoT，避免 token 浪费与"过度推理"

### 1.2 结构化输出

Agent 的规划/路由结果必须**可被代码消费**，因此需要结构化输出，常用三种方式：

| 方式 | 说明 | 适用 |
|------|------|------|
| JSON mode | 模型输出严格 JSON，代码解析 | 路由结果、工具参数 |
| Pydantic 校验 | 定义模型类，解析时强校验 | 复杂嵌套结构 |
| Function Calling | 模型直接输出工具调用 schema | 工具调用场景 |

Mitta 的 Query 改写节点即用 JSON mode + Pydantic：

```python
resp = model.invoke(prompt, response_format={"type": "json_object"})
result = QueryRewriteResult(**extract_json(resp.content))
queries = [result.main_query] + result.sub_queries
```

**要点**：解析失败要兜底（`extract_json` 容错），不能让结构化解析异常中断主流程。

## 二、意图识别与路由

### 2.1 为什么需要路由

不同输入走不同链路才能兼顾质量与成本：
- 检索问答 → 走 RAG 子图（召回+重排，贵）
- 闲聊/寒暄 → 直接生成（便宜）
- 动作请求 → 调工具
- 身份/人格问题 → 按角色回答

### 2.2 路由实现方式

| 方式 | 优点 | 缺点 |
|------|------|------|
| 关键词规则 | 快、零成本 | 覆盖差，无法处理语义 |
| LLM 分类 | 语义准确、可扩展 | 有延迟与成本、存在波动 |
| 向量相似度 | 快、无需 LLM | 依赖样本质量 |
| 混合（规则兜底+LLM） | 稳 | 实现复杂 |

### 2.3 Mitta 统一路由（实测口径）

Mitta 在路由节点**一次调用同时判定两个维度**：

- **意图维度**：是否走检索（37 条统一评测，意图判定准确率 **91%~94%**，两次 temperature=0 重跑仍有波动，报区间不报单点）
- **人格维度**：四分类（正常/友善/简短/多语），**32/32 = 100%**，两次稳定

**关键经验**：
1. 路由结果必须**可回退**：检索召回空时自动降级为纯生成，不让路由错误导致空回答
2. 评估要有**双维度标签**：同一 query 同时标注意图与人格，一次调用评估两件事
3. 固定 `temperature=0` + 多次投票取众数，降低采样波动

## 三、工具选择规划

工具多了之后，"该用哪个工具"本身就是规划问题。Mitta 采用**规则层 + 语义层并集召回**：

```
候选工具 = 规则层命中（tags 关键词匹配） ∪ 语义层命中（工具名/描述向量检索）
```

- **规则层**：按工具 tag 关键词精准命中，快且可解释
- **语义层**：把工具名+描述向量化，语义相近也能召回（如"查时间"命中 get_current_time）
- **并集去重**：两侧合并去重，保召回优先（41 工具 22 用例 avg_recall 0.8939、零空结果）
- **降级熔断**：语义层异常自动降级规则层；同一工具连续失败 2 次从本轮摘除（评测 13/13）

**为什么保召回不保精确**：工具选择宁可多给候选（top-12）让 LLM 再筛，也不漏掉正确工具——漏了就无法完成任务；代价是 precision 低（结构性，非实现缺陷）。

## 四、规划 vs 反应式

| 维度 | 反应式（Reactive） | 规划式（Planning） |
|------|-------------------|--------------------|
| 决策时机 | 每一步根据当前状态决定 | 先产出整体计划再执行 |
| 延迟 | 低（边想边做） | 高（先规划） |
| 复杂任务 | 容易迷失目标 | 更稳 |
| 实现 | 简单 | 需计划校验/修正机制 |

**工程建议**：多数对话场景用反应式（快）；长任务、多步骤任务（如"调研后写报告"）用规划式。Mitta 主图本质是"轻量规划 + 反应式执行"：路由决定链路，链路内固定执行。

## 五、FAQ

**Q1：路由用 LLM 还是规则？**
视预算与准确率要求。规则便宜但覆盖差；LLM 准但贵且波动。推荐**规则兜底 + LLM 主判**：LLM 判不出的情况落规则分支，保证零遗漏。

**Q2：意图分类准确率怎么评估才可信？**
至少两条：① 双轮重跑看波动（temperature=0 下仍有采样差异，报区间）；② 边界用例单独建集（易混淆 query 如"帮我查一下"是检索还是动作），否则指标虚高。

**Q3：工具越来越多，如何避免选错工具？**
① 工具名与描述写清楚（描述即索引）；② 规则 tags + 语义向量双路召回；③ 失败熔断防止反复踩坑；④ 关键工具加参数校验，调用错误能给出可读报错。
