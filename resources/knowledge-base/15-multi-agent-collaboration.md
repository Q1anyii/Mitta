# 多智能体协作

> 基于 AgentProject 项目总结，涵盖多智能体协作模式（Supervisor / Hierarchical / Swarm / Agent Team）、
> 通信机制、职责边界与治理，以及 Mitta 项目四 Agent 工程治理的实际实践。

## 一、为什么需要多智能体

单 Agent 的局限：
- **上下文污染**：所有能力塞进一个上下文，互相干扰
- **职责不清**：规划/写代码/写文档/问答混在一起，难以复用
- **单点失败**：一个环节出错拖垮整个任务

多智能体把复杂系统**拆成多个专职 Agent**，各自独立上下文、独立职责，通过协作完成整体任务。

## 二、主流协作模式

### 2.1 Supervisor（监督者模式）

一个"主管" Agent 负责调度，子 Agent 各司其职：

```
                    ┌──────────────┐
用户请求 → Supervisor（路由/调度）──→ Worker A（检索）
                    │              └──→ Worker B（工具）
                    │              └──→ Worker C（生成）
                    └──────────────┘
```

- **优点**：职责清晰、可扩展（加 Worker 即可）、主管可做全局决策
- **缺点**：主管是瓶颈与单点，调度成本高
- **适用**：任务类型多样、需要统一入口的系统

### 2.2 Hierarchical（层级模式）

多级监督，上级 Agent 管理下级 Agent，适合大型任务树。缺点：层级深则延迟高、错误传导。

### 2.3 Swarm（群体模式）

Agent 之间**动态交接控制权**（handoff），没有固定主管，任务在 Agent 间流转。灵活但难追踪、难保证一致性。

### 2.4 Orchestrator-Worker（编排-执行）

编排器拆解任务、分派 Worker 并行执行、汇总结果。适合可并行子任务的场景（如并行检索、并行调研）。

### 2.5 Agent Team（智能体团队）

多个 Agent 围绕一个目标协作，可动态组队、共享上下文与工具，是业界探索方向（如 Claude Code 的 sub-agent、CrewAI 的 crew）。

## 三、通信机制

| 机制 | 说明 | 适用 |
|------|------|------|
| 共享状态 | 所有 Agent 读写同一状态（如 LangGraph State） | 单进程编排 |
| 消息传递 | Agent 间显式发消息 | 分布式、跨会话 |
| 文件总线 | 落盘传递结构化文档（交接文件） | 异步、可审计 |
| 函数调用 | Agent 通过工具调用其他 Agent | 按需委派 |

## 四、Mitta 四 Agent 工程治理实践

Mitta 项目本身用**多 Agent 协作**做工程治理（非产品功能，而是开发流程）：

| Agent | 职责 | 产出 |
|-------|------|------|
| 对接专员 | 需求分析、方案设计 | 交接说明（handoff 文件） |
| 开发 Agent | 编码、优化、提交 | 代码 + devlog |
| 文档撰写 Agent | 项目详解、README 同步 | 文档 |
| 检索 Agent | 基于权威索引回答项目细节 | 问答（只读） |

**治理要点（对多智能体系统设计的启示）**：

1. **唯一权威契约**：`AGENTS.md` 定义职责边界，`.agent/*.md` 就近提醒，冲突以根契约为准，避免"一处三写漂移"
2. **文件总线落盘**：跨 Agent 传递经 `.agent/handoff/H-*.md` 落盘，不靠对话复制粘贴——状态不活在对话里，下一个角色才能读到
3. **状态机化交接**：handoff 文件带 `status: open/done`，任何角色开局扫非 done 的即当前待办
4. **防重复**：同步标记只写在 devlog（`docs_sync: required/none`），handoff 用 `devlog:` 指针指向，不重复登记
5. **自检脚本**：`.agent/check.py` 只读检查滞留交接、同步标记、治理一致性，退出码 0/1 供自动化判断
6. **角色漂移重开**：发现 Agent 越界（开发写文档、检索改代码）时**重开新会话**而非会话内纠偏，避免带错上下文继续

## 五、设计原则

1. **职责互不重叠**：每个 Agent 只做一类事，边界写进契约，否则上下文污染
2. **默认少跳数**：手动搬运成本随跳数线性增长，默认两跳（对接→开发），文档同步按标记触发
3. **可审计**：所有交接落盘、标记可查、自检可跑
4. **明确失败归属**：Agent 遇到职责外的事，打标记提示对应角色，不越界代做
5. **评估独立**：每个 Agent 的产出有验收口径（如文档可追溯提交 sha、无旧口径残留）

## 六、FAQ

**Q1：多智能体一定比单 Agent 好吗？**
不一定。多智能体带来编排成本、延迟、一致性问题。**先单 Agent 跑通，复杂度上来了再拆**；拆的标准是"上下文互相污染"或"职责明显可分"。Mitta 的工程治理多 Agent 是开发流程，产品侧仍是单 Agent 主图 + 混合路由。

**Q2：Supervisor 模式的瓶颈怎么破？**
主管单点：① 主管只做路由不做重活；② 主管失败降级为规则路由；③ 热点 Worker 可水平扩展；④ 记录调度轨迹便于排查。

**Q3：Agent 之间怎么防"互相打架"（重复/冲突）？**
① 唯一权威源（如单一契约文件）；② 状态机化交接（open/done）；③ 写操作加锁/幂等；④ 自检脚本周期校验一致性。
