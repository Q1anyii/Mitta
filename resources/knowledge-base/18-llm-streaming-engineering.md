# LLM 流式与接口工程

> 基于 AgentProject 项目总结，涵盖 SSE 流式输出、首 token 优化、超时与重试、
> 上下文与 token 管理、成本控制，以及 Mitta 对话 API 与预响应优化的实际实现。

## 一、SSE 流式输出

SSE（Server-Sent Events）是 LLM 对话常用的流式传输协议：服务端持续推送事件，客户端逐块渲染，用户无需等待完整生成。

```
GET /api/chat  →  200 text/event-stream
data: {"event": "start", "session_id": "..."}
data: {"event": "token", "content": "你好"}
data: {"event": "done", "usage": {...}}
```

**实现要点（FastAPI）**：

```python
from fastapi.responses import StreamingResponse

async def chat_stream():
    async for chunk in llm_stream():
        yield f"data: {json.dumps(chunk, ensure_ascii=False)}\n\n"

return StreamingResponse(chat_stream(), media_type="text/event-stream")
```

- 事件类型化：start / token / done / error 区分，前端按事件渲染
- 心跳保活：长连接防止代理/网关超时断开
- 前端 AbortController：用户停止生成时中断请求，服务端取消 LLM 流

## 二、首 token 优化

首 token 延迟（TTFT）是用户体感关键指标。Mitta 的优化组合：

| 手段 | 效果 |
|------|------|
| 缓存命中跳过检索子图 | 改写/召回/重排全跳过，生成照常 |
| 检索期预响应 | 检索进行时先行推送开场白 + 思考 loading，消除 7s 空白等待 |
| 检索并行化 | 多路召回并行执行，改写前置依赖最小化 |
| 记忆 fire-and-forget | 记忆更新与生成解耦，正文流完即结束加载态 |

**实测口径**（线上每场景 n=3）：
- 短路场景首 token p50 ≈ 1.6s
- 非检索场景 ≈ 1.9s
- 检索场景 ≈ 12.3s（检索链路占大头，预响应已消除空白感）

## 三、超时与重试

| 场景 | 策略 |
|------|------|
| LLM 调用 | 客户端超时 + 指数退避重试，避免网络抖动 |
| MCP 工具 | 长任务工具超时调至 120s，避免误杀 |
| Redis | socket_timeout 5s，失败降级内存实现 |
| 上游 API | 重试上限 + 熔断（连续失败摘除） |

**重试注意**：
- 幂等操作才可安全重试（读操作可，写操作需幂等键）
- 重试要有退避（不能死循环），记录重试次数
- 超时与重试配合：超时触发重试，重试上限后降级或报错

## 四、上下文与 token 管理

上下文窗口有限，管理是长期工程：

1. **窗口裁剪**：保留最近的 N 轮，超长截断（Mitta 保留多轮追问所需上下文）
2. **摘要压缩**：早期对话压缩为摘要，替代原文
3. **记忆外置**：长期信息进记忆/知识库，按需召回，不全量入上下文
4. **工具结果截断**：工具返回长文本截断（如 200 字）再入上下文
5. **检索文档数量上限**：`MAX_RETRIEVAL_DOCS=8`，防上下文爆炸

## 五、成本控制

| 手段 | 机制 | 效果 |
|------|------|------|
| 缓存命中 | 跳过检索子图（改写/召回/重排） | embedding 调用降 12.5%（实测） |
| 路由分流 | 闲聊走生成，检索才走 RAG | 避免无谓检索 |
| 工具轮次上限 | MAX_TOOL_ROUNDS=8 | 防失控循环烧钱 |
| 模型分级 | 简单任务用小模型，复杂任务用大模型 | 成本弹性 |
| 限流 | Redis 滑动窗口 30 次/60s | 防刷量 |

**成本估算**：单次成本 = token 单价 × 消耗量（输入 + 输出 + 缓存命中价差）；评估时要区分"检索路径"与"短路路径"的单价差异。

## 六、接口工程规范

- **错误码统一**：业务异常（401/403/404/429/500）语义清晰，前端可映射
- **幂等设计**：提醒投递等写操作用唯一键幂等去重（INSERT IGNORE 抢占，at-most-once）
- **降级透明**：Redis 挂了限流降级内存版仍工作；检索失败降级纯生成，不空回答
- **日志可观测**：记录首 token、总时长、token 消耗、缓存命中、工具调用轨迹

## 七、FAQ

**Q1：SSE 与 WebSocket 怎么选？**
SSE 单向服务端推送、基于 HTTP、自动重连，适合 LLM 流式输出；WebSocket 双向、适合实时交互（如协同编辑）。对话流式用 SSE 足够且更简单。

**Q2：首 token 慢一定是 LLM 慢吗？**
不一定。Mitta 实测检索场景首 token 12.3s 大头在检索链路（改写→召回→重排串行），不是生成。定位要分层打点：路由耗时、检索耗时、首 token 生成耗时分别统计。

**Q3：长对话上下文爆了怎么办？**
分层：窗口裁剪（保留最近轮）+ 摘要压缩（早期对话）+ 记忆外置（关键事实进长期记忆）。不要"全保留"，成本与质量平衡。
