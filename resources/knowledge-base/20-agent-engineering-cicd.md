# Agent 工程化与部署

> 基于 AgentProject 项目总结，涵盖项目结构分层、配置管理、缓存体系、限流降级、
> CI/CD 与蓝绿部署、监控日志，以及 Mitta 从开发到线上稳定运行的工程实践。

## 一、项目结构分层

```
src/
├── graphs/        # LangGraph 主图与子图（路由/检索/记忆/工具）
├── routers/       # FastAPI 路由层（对话/知识库/认证/管理）
├── service/       # 业务服务层（知识库、缓存、MCP 客户端）
├── mcp_client/    # MCP 工具客户端（连接/发现/调用/健康检查）
├── vector/        # 向量库与嵌入（EmbeddingProcessor、vector_store）
├── middleware/    # 中间件（限流、认证、CORS）
├── schemas/       # Pydantic 模型
├── constant/      # 常量与提示词
├── utils/         # 工具函数
└── agent_test/    # 评测（原 ragas_test 改名）
```

**分层原则**：路由层只做参数校验与响应封装，业务逻辑在 service 层，AI 编排在 graphs 层，数据访问在对应 store——改动隔离、可单测。

## 二、配置管理

| 配置 | 文件 | 说明 |
|------|------|------|
| 密钥/环境 | `.env` | API Key、数据库连接、Redis 地址 |
| 向量库 | `resources/config/vector_db.json` | 类型（chroma）、持久路径、collection 名 |
| MCP 服务器 | `resources/config/mcp_servers.json` | 第三方工具注册（免改代码） |
| 系统提示 | `resources/system_prompt/` | 角色/行为/风格 |
| 常量 | `src/constant/` | 工具轮次上限、检索文档数、截断长度 |

**要点**：
- 密钥只进 `.env`，代码不硬编码，日志脱敏
- 配置校验：启动时校验必填项（Mitta 环境变量校验，缺失即报错）
- 路径配置独立（vector_db.json），切换向量库不碰代码

## 三、缓存体系（Mitta 四层）

| 层 | 缓存什么 | 命中效果 |
|----|----------|----------|
| L1 | Query 改写结果 | 跳过改写（链路最贵节点，占 45% 耗时） |
| L2 | 检索向量缓存 | 跳过召回 |
| L3a | 精确匹配（指纹去重） | 跳过整个检索子图 |
| L3b | 语义缓存（LSH 分桶 + KNN + reranker 阈值） | 跳过检索子图，生成照常 |

**语义缓存命中率实测（E6-B）**：
- 隔离会话：97.2%（35/36）
- 混合会话 12 条 + 候选 3（生产默认）：61.1%
- 候选 12：88.9%
- 误命中：硬负 0/8 + 跨域 0/6（0%）
- embedding 调用降 12.5%（24 query 实测）

**缓存设计要点**：
- 缓存 key 按 tool_status + 轮次设计，避免跨轮误命中
- 命中只跳检索子图，生成照常执行（保质量）
- 语义层异常自动降级规则层（精确匹配），熔断防故障

## 四、限流与降级

```
限流：Redis ZSET 滑动窗口（30 次/60s）
  └─ Redis 异常 → 自动降级内存 deque 滑动窗口（仍可限流）
工具：语义召回失败 → 降级规则层
  └─ 工具连续失败 2 次 → 熔断摘除（13/13 评测）
检索：检索失败/空 → 降级纯生成
记忆：fire-and-forget → 不阻塞正文流
```

**降级原则**：宁可功能降级（少检索/少工具），不可整体不可用；每条降级路径都要可观测（日志 + 计数）。

## 五、CI/CD 与部署

### 5.1 GitHub Actions 全自动流水线

```
push → 构建镜像 → 测试 → 推送镜像 → 部署服务器 → 健康检查 → 通知
```

**Mitta 实践要点**：
- **蓝绿入库切换**：知识库入库到新 collection，验证后切换，可 `cleanup --keep` 保留回滚
- **rsync 增量部署**：替代全量 SCP，只同步变更文件（快、省带宽）
- **健康检查**：部署后 HTTP 探活，多次失败即判失败（第 N 次 HTTP 000000 → 失败退出）
- **MCP 预装**：Dockerfile 预装 MCP 包（uv tool install），容器启动即用

### 5.2 低配服务器调优（Mitta 实测）

1 核 1.6G 容器下的取舍：
- 停用重量级组件（Milvus/etcd/minio）→ 嵌入式 ChromaDB
- 增加 swap，内存占用从 85% 降到约 60%
- 模型 API 外置（SiliconFlow），不本地跑模型
- 缓存 + 路由分流降低峰值负载

### 5.3 域名与 HTTPS

- Nginx 反向代理 + SSL 证书（www.mittaai.xyz）
- 前端静态资源与 API 同域，避免 CORS 问题
- 容器内部端口不直接暴露，Nginx 统一入口

## 六、监控与日志

- **结构化日志**：loguru 分级（INFO/WARNING/ERROR），关键节点打点
- **评测报告归档**：`src/agent_test/reports/<日期>/`，可对比历史
- **devlog 机制**：重要 bug 修复/功能变更写开发日志，带 `docs_sync` 标记驱动文档同步
- **治理自检**：`.agent/check.py` 周期检查交接/同步/一致性（退出码供自动化）
- **性能打点**：首 token、总时长、token 消耗、缓存命中、工具调用轨迹

## 七、FAQ

**Q1：蓝绿部署和滚动部署选哪个？**
蓝绿：整批切换，回滚快（切回旧 collection），适合知识库/版本敏感场景；成本高（双倍资源）。滚动：逐个替换，省资源，但新旧共存期有兼容问题。Mitta 知识库用蓝绿（collection 切换），应用本身滚动 + 健康检查。

**Q2：1.6G 内存能跑 Agent 服务吗？**
能，靠取舍：外置模型 API、嵌入式向量库、swap、缓存降峰、限流防滥用。代价是并发低、重任务慢；流量上来后需升级（2C4G 起步，向量库可独立部署）。

**Q3：健康检查为什么要多次重试？**
服务启动需要时间（依赖初始化、MCP 连接、向量库加载），立即探测会误判失败。Mitta 多次探测（指数间隔），启动窗口内不放弃，启动后快速暴露真实故障。
